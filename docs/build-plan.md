# Build plan

The end-to-end build in eight phases, in dependency order. Phases 1–5 form the core loop; 6–7 layer on top; 8 ships it. See [product.md](product.md) for what each feature does.

| #   | Phase                            | What gets built                                                                                                                                                                                                                                                                                                                                                          | Done when                                                                                                     |
| --- | -------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------------------------- |
| 0   | **Foundations** ✅               | Project skeleton, hash-chained evidence ledger, council vote aggregation, docs                                                                                                                                                                                                                                                                                           | Done                                                                                                          |
| 1   | **PayPal sandbox and client** ✅ | Run the tests in [spike-results.md](spike-results.md). Real PayPal client (MCP first, REST fallback). Webhook receiver with signature verification. Seed script v1: invoice → pay with balance → open dispute.                                                                                                                                                           | One command creates a real sandbox dispute, and the spike results are recorded                                |
| 2   | **Server core** ✅               | Database schema (sellers, buyers, deals, scope versions, milestones, artifacts, ledger, webhook events); the disputes and packets tables are added in Phase 5. Ledger persisted. File storage with SHA-256 fingerprints. Seller sign-in with PayPal and buyer magic links.                                                                                               | A deal can be created and every change appears in a verifiable ledger                                         |
| 3   | **AI layer** ✅                  | Model registry and OpenAI-compatible client. Council runner (answer → validate → anonymize → rank → aggregate) built on `packages/council`. Prompts, JSON schemas, citation validator. First tasks: scope drafting, category check, vague-word rewrites. Prompt-injection test set. Evals harness comparing single model and council.                                    | A pasted chat becomes a cited scope through the council, and evals report a number                            |
| 4   | **Deal lifecycle** (happy path)  | New deal (paste, upload, email or Zapier; screenshots of chats are read to text and checked by the seller). Scope editor. Buyer acceptance page with Q&A, receipt PDF and email. Milestone invoices and payment webhook. Delivery links with access log, approve or request changes. Pre-delivery check. Message watcher and change orders. Evidence completeness score. | The Maya story runs from chat to final download in the sandbox                                                |
| 5   | **Dispute and appeal**           | Disputes and packets tables. Dispute intake by webhook or polling, matched to deals. Dispute workspace with deadline and allowed actions. Claim-vs-record (council). Packet PDF builder with size meter. Confirm and upload evidence. Offers limited to allowed types. Appeal check and submission. Deadline reminders on Render Workflows.                              | Maya's and Jun's disputes get real evidence uploads; Daniel's appeal check works (real, or a labelled replay) |
| 6   | **Seller connection**            | "Connect with PayPal" via Partner Referrals with `PayPal-Auth-Assertion`; fallback where sellers connect their own sandbox app                                                                                                                                                                                                                                           | A second sandbox seller connects and has invoices and disputes handled on their behalf                        |
| 7   | **Agents and partner tools**     | MCP server for agents with confirm tokens. AG Grid tables, Bryntum Gantt and calendar. KERNEL website snapshots. Channel3 product details for goods. Postman workspace. APIMatic SDK and portal from the OpenAPI spec. Zapier intake. Astropods for agent hosting and evals.                                                                                             | Each partner tool has one real, visible use                                                                   |
| 8   | **Ship**                         | Deploy on Render (app, Postgres, Workflows) with seeded demo deals. README, tools explanation and eval numbers. Security and privacy pass. Demo video. Merge `dev` into `main`, make the repo public, submit on Devpost.                                                                                                                                                 | Submission confirmed, at least a day before the deadline                                                      |

## Dependencies

- **1 → 2 → 3 → 4 → 5 is the critical path.** After phase 5 the full demo story works end to end.
- **Phase 3 can run alongside 1–2**: it needs model keys, not PayPal.
- **Phases 6 and 7 sit on top** and do not block the core loop; the demo can run on a seller's own connected app if partner onboarding is delayed.

## Open points

Gaps and questions found while building, so they are not lost. Each says where it will be picked up.

| Point                                                                                                                                                                                                                                                                                                                                                                                                                                                                            | Where                                                           |
| -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------- |
| **Buyer duties and deadlines** (solved in 4n): drafts made with prompt version 3 list what the buyer must provide, with dates, and the editor pre-fills them as suggestions. The 4n-2 eval run measures how often they are found.                                                                                                                                                                                                                                                | Draft part in 4n                                                |
| **Wording suggestions can invent specifics and repeat themselves.** Prompt version 2 (3fb) tells the models to list each phrase once and not to add tools, technical choices, sizes or conditions; one live run on the bakery chat showed no invented specifics, but one suggestion adds a number ("within 48 hours"). A single run proves little.                                                                                                                               | Measure in 3g                                                   |
| **Ties and the two-draft vote** (3h): when the council cannot rank its drafts the page now says so and lets the seller choose; the council's own tie-breaks are unchanged. Look again at how often it happens once a second eval run is in.                                                                                                                                                                                                                                      | 3h done; re-check with the next eval run                        |
| **Screenshots of chats** are read to text by a vision model and checked by the seller before drafting.                                                                                                                                                                                                                                                                                                                                                                           | Phase 4 (New deal)                                              |
| **Groq's per-minute limit** can reject one of the two Groq models when all models start together. The client now waits as the host asks; staggering the two Groq calls is an optional extra.                                                                                                                                                                                                                                                                                     | Only if 429s keep happening                                     |
| **Nemotron (free) is slow and sometimes times out**; it can stretch a council run to 90 seconds. In the 3g evals all its calls were rate limited; in eval run 2 (4n-2) it scored best (0.99, no wrong values) but took 42 seconds and 5,421 tokens per draft.                                                                                                                                                                                                                    | Decide after a second eval run on a day its limit has reset     |
| **Free-tier limits cap the council.** Gemini (this key): 20 requests a day for gemini-3.6-flash, so about 10 council runs a day. OpenRouter free models: 50 requests a day (1,000 with 10 credits). Groq gpt-oss: 8,000 tokens a minute. A demo day or an eval run can exhaust them and leave the council with one or two models. Options: link billing to the Google AI project (the owner has credits), add 10 credits on OpenRouter or drop Nemotron, stagger the Groq calls. | Owner's decision before the demo and before the 3g evals        |
| **Injection defences (3fb):** orders to an AI are hidden by pattern, cannot be quoted, and are shown to the seller; a prompt rule backs this up. The pattern list can be got round by orders worded differently. gpt-oss without hiding could not be measured (Groq limit spent).                                                                                                                                                                                                | Re-measure in 3g with more runs and when Groq's limit has reset |
| **Hosts' data terms** for pasted chats have not been checked; only made-up chats are used. The same goes for Resend (4c), which carries buyers' and sellers' email addresses, buyer links and receipts.                                                                                                                                                                                                                                                                          | Phase 8 (privacy pass), before any real chat                    |
