# Decisions

A running log of design decisions and the reasons behind them. Newest decisions are added at the bottom of each section.

## Product

| Decision                                                                                       | Reason                                                                                                                                                                                                               |
| ---------------------------------------------------------------------------------------------- | -------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| Name: **PactPal**                                                                              | Follows PayPal's two-part pattern (what you do + why you trust it). No conflicting product or USPTO mark found; `pactpal.com` was available at the time of checking.                                                 |
| Primary user is the **seller** (freelancer, creator, small business paid via PayPal)           | Buyers open disputes; sellers are the ones who need a defense. Buyer features are advisory only.                                                                                                                     |
| Core idea: create evidence **at the time of the deal**, not after a dispute opens              | Existing dispute tools rebuild evidence after the fact. Records made with the buyer's explicit agreement are stronger and cheaper.                                                                                   |
| No escrow, no holding funds                                                                    | PayPal's user agreement states PayPal is not an escrow agent, and holding funds raises money-transmission questions. Milestone invoices give the same structure.                                                     |
| No buyer-side claim filing                                                                     | Buyers must file claims themselves in PayPal's Resolution Center.                                                                                                                                                    |
| Never promise outcomes                                                                         | The product reports "evidence completeness", never "you will win" or that Seller Protection applies.                                                                                                                 |
| Sellers can use PactPal for **services and digital work** (focus) and **small physical goods** | These are where PayPal disputes reach sellers directly and proof of scope, delivery and approval is hardest. Physical goods with tracking already have stronger protection, so they are supported but not the focus. |
| **Deposit bookings, retainers and regulated services are blocked** ("not supported yet")       | More dispute-prone and rule-heavy (cancellation terms, professional regulation). On the roadmap.                                                                                                                     |
| PayPal-prohibited categories and high-risk extras are blocked                                  | Gift cards and stored value, crypto, NFTs and investments, vehicles and real estate, plus everything in PayPal's Acceptable Use Policy. See [scope.md](scope.md).                                                    |

## AI

| Decision                                                                                    | Reason                                                                                                                                                                                                                                                                                                    |
| ------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| AI drafts, humans decide                                                                    | AI never creates evidence, timestamps or approvals. Every send to a buyer or to PayPal needs explicit confirmation.                                                                                                                                                                                       |
| Citations or blank                                                                          | Every AI-drafted field or sentence must cite a source line or ledger event id; otherwise it stays blank. Code checks this.                                                                                                                                                                                |
| AI across the whole deal                                                                    | Scope drafting from chat, pre-delivery scope check, message watcher for scope creep, buyer Q&A answered only from the agreement, claim-vs-record breakdown when a dispute opens, appeal check.                                                                                                            |
| **LLM council** for high-stakes tasks (scope extraction, claim-vs-record, appeal statement) | Independent models cross-check each other. Answers failing code validation are dropped, the rest are anonymized and ranked by every member, a Borda count picks one whole answer, and low agreement flags the result for human review. Prior work: Karpathy's LLM Council and Mixture-of-Agents research. |
| Single fast model for frequent tasks (message watcher, buyer Q&A)                           | Latency and cost.                                                                                                                                                                                                                                                                                         |
| **Open-model council** (different families, e.g. Llama, Mistral, Qwen) via hosted APIs      | Diversity across model families, low cost. The registry accepts any OpenAI-compatible endpoint, so closed models can be added if evals show a gap. Hosted only, no local mode.                                                                                                                            |
| Measure, don't claim                                                                        | Evals compare single-model and council results on a fixed test set before any claim is made in the submission.                                                                                                                                                                                            |
| **AI category check**                                                                       | While drafting the scope, the AI also classifies what is actually being sold from the conversation. A mismatch with the seller's chosen category is flagged; a blocked category stops the deal. The notice is logged in the ledger.                                                                       |
| Proposed council hosts: Llama via Groq, Mistral via Mistral's API, Qwen via OpenRouter      | Three model families from three different companies, each with a free tier or low cost. Pending sign-up; the registry makes swapping a host a config change.                                                                                                                                              |

## PayPal integration

| Decision                                                                                                                                                                                  | Reason                                                                                                                                                                                                                                                                                                             |
| ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------ |
| **MCP first, REST fallback**                                                                                                                                                              | Each operation tries a PayPal MCP tool first (Agent Toolkit or the hosted sandbox MCP) and falls back to REST if the tool is missing, errors or times out. Operations without an MCP tool (evidence, offers, appeals, messages, webhook verification) use REST directly. The transport used is recorded and shown. |
| Sellers connect their own PayPal account                                                                                                                                                  | Main path: Partner Referrals ("Connect with PayPal") with invoicing and dispute permissions, calling on the seller's behalf with `PayPal-Auth-Assertion` (payer id, not email). Fallback: the seller connects their own sandbox REST app.                                                                          |
| Webhooks as the source of truth, polling as backup                                                                                                                                        | Dispute webhooks may not reach a platform for every seller; the dispute list is polled per seller as a backup.                                                                                                                                                                                                     |
| Read allowed actions from PayPal every time                                                                                                                                               | Allowed actions and offer types change with dispute state; never assume them. Dispute writes are sent one at a time.                                                                                                                                                                                               |
| US sandbox accounts                                                                                                                                                                       | Sandbox capabilities vary by country; US accounts support the full flow.                                                                                                                                                                                                                                           |
| Test disputes via a second business account                                                                                                                                               | A sandbox business account acting as the buyer can create disputes through its own REST app. Packaged as a sandbox seed script.                                                                                                                                                                                    |
| Access tokens cached in memory per app, renewed 5 minutes before expiry; concurrent callers share one login; a rejected token is renewed once                                             | Tokens last about nine hours. Renewing early avoids a token expiring mid-request, and sharing one login avoids a burst of logins when many requests start together.                                                                                                                                                |
| Every PayPal call: 15-second time limit, up to 3 tries with exponential backoff and jitter, retrying only network errors, 429 and 5xx                                                     | Transient sandbox failures (for example intermittent 500s on refunds) are common. Client errors (4xx) are never retried because repeating them cannot succeed.                                                                                                                                                     |
| Writes must carry a stable `PayPal-Request-Id`, enforced by the types; retries reuse it                                                                                                   | PayPal treats repeats with the same id as one request, so a retry after a lost answer can never create a second invoice, refund or evidence upload.                                                                                                                                                                |
| An app's permissions are read from its login answer (`pnpm sandbox:check`)                                                                                                                | The token response lists every granted permission, so feature checks need no extra calls and change nothing in the sandbox.                                                                                                                                                                                        |
| PayPal MCP is reached over SSE (`https://mcp.sandbox.paypal.com/sse`) with the official MCP SDK                                                                                           | The documented streamable HTTP address returned 404 while `/sse` connected. The SDK marks SSE as deprecated, so the address is one setting to change when PayPal's HTTP endpoint works.                                                                                                                            |
| MCP attempts have a 10-second limit; after 3 MCP failures in a row MCP is skipped for 10 minutes                                                                                          | While MCP is broken, every call would otherwise wait on it first. Each result records `mcp` or `rest` and the reason for falling back.                                                                                                                                                                             |
| A write falls back to REST only when MCP certainly did not do it (no connection, or PayPal answered with an error); after a timeout or an unreadable answer the write fails instead       | PayPal's MCP tools accept no request id, so REST could not recognise a repeat and might create a second invoice or upload. Reads always fall back.                                                                                                                                                                 |
| Invoice amounts are passed as whole minor units with a currency code and converted to PayPal's decimal strings only at the PayPal boundary (no decimals for JPY, HUF, TWD)                | Matches the money rule in the engineering standards and avoids floating-point errors.                                                                                                                                                                                                                              |
| One invoice per milestone is created and then sent as two writes with fixed request ids (`<id>` and `<id>-send`); a failed send reports the created invoice id                            | Both steps can be retried safely, and a created-but-unsent invoice is never lost or duplicated.                                                                                                                                                                                                                    |
| The scope reference is written into the invoice note as "Agreed scope: …"                                                                                                                 | The buyer sees what the payment is for, and the invoice links back to the signed scope in disputes.                                                                                                                                                                                                                |
| Dispute listing follows PayPal's next links up to 10 pages of 50, and says when it stopped early                                                                                          | Nothing is silently missed, and a broken pagination answer cannot loop forever.                                                                                                                                                                                                                                    |
| Dispute reasons, statuses, stages and outcomes are kept as PayPal's own text, not a fixed list                                                                                            | PayPal adds values over time; an unknown value is shown rather than rejected.                                                                                                                                                                                                                                      |
| What the seller may do on a dispute is read from its action links each time (all but `self`), and offer types from `allowed_response_options.make_offer`                                  | Allowed actions change with the dispute's state and must never be assumed.                                                                                                                                                                                                                                         |
| Every dispute answer (evidence, offer, accepting the claim, appeal) re-reads the dispute first and is refused unless PayPal allows that action, and for offers that offer type, right now | A refused answer costs nothing; a wrong one sent to PayPal is hard to undo.                                                                                                                                                                                                                                        |
| Answers to the same dispute are queued and sent one at a time; a refused or failed answer does not block the next                                                                         | PayPal briefly locks a dispute after each seller write and refuses a second one.                                                                                                                                                                                                                                   |
| Evidence and appeal files are checked by their first bytes (PDF, PNG, JPEG, GIF), must have a plain name, and must be 1 byte to 10 MB                                                     | A renamed file cannot slip through, and bad files are reported before any upload.                                                                                                                                                                                                                                  |
| Accepting a claim tries PayPal's MCP tool only for a full refund with a note of letters, digits, `_` or `-`; other answers use REST directly                                              | The MCP tool takes no refund amount and only that note format; evidence, offers and appeals have no MCP tool.                                                                                                                                                                                                      |
| `pnpm sandbox:respond` is a dry run unless `--send` is given                                                                                                                              | Nothing goes to PayPal without a person explicitly choosing to send it.                                                                                                                                                                                                                                            |
| The server is hosted on Render, described in `render.yaml` (a Blueprint), deploying the `dev` branch on each commit                                                                       | Render is a hackathon sponsor with its own track, PayPal needs a public address for notifications, and a Blueprint keeps hosting versioned and repeatable.                                                                                                                                                         |
| Starter instance (always on, 0.5 CPU, 512 MB), paid from the hackathon's Render credit                                                                                                    | The free instance sleeps after 15 minutes and takes about a minute to wake, delaying PayPal notifications and demos.                                                                                                                                                                                               |
| Render region: Virginia (US East)                                                                                                                                                         | Nearest to the developer (US) and to PayPal's US systems; a Render service's region cannot be changed after it is created.                                                                                                                                                                                         |
| Webhook verification sends PayPal the received body byte for byte inside the verify request                                                                                               | Re-serialising the event can change its bytes and make genuine notifications fail verification.                                                                                                                                                                                                                    |
| Webhook answers: 200 handled or repeat, 400 not genuine or malformed, 500 PayPal could not be asked (so PayPal retries), 503 not configured                                               | PayPal retries non-2xx answers; only temporary problems should be retried.                                                                                                                                                                                                                                         |
| Seen notification ids are kept in memory (newest 10,000) until Phase 2 moves them to Postgres                                                                                             | Repeats are skipped now; today handling only logs, so a repeat after a restart is harmless.                                                                                                                                                                                                                        |
| The server bundle includes the npm libraries of workspace packages; only the server's own dependencies stay external, and the build fails if any external import cannot be resolved       | pnpm keeps each package's dependencies private, so the built server could not find the MCP library; this was caught before the first Render deploy.                                                                                                                                                                |

## Engineering

| Decision                                                                                                                              | Reason                                                                                                                                                                                                                                                                      |
| ------------------------------------------------------------------------------------------------------------------------------------- | --------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| TypeScript end to end (React + Vite, Node + Fastify, Postgres)                                                                        | One language; first-class support in the partner tools and the PayPal Agent Toolkit.                                                                                                                                                                                        |
| Hash-chained, append-only ledger                                                                                                      | Each entry includes the previous entry's hash, so edits, backdating and deletions are detectable. Corrections are new events.                                                                                                                                               |
| MIT license                                                                                                                           | Simple and widely understood.                                                                                                                                                                                                                                               |
| Written engineering standards with an automated gate (`pnpm verify`)                                                                  | Production-grade quality must not depend on memory. Formatting, types, strict lint, coverage, duplicate code, architecture boundaries and dependency vulnerabilities are checked by tools; see [engineering-standards.md](engineering-standards.md).                        |
| CI runs the same gate on every push and pull request                                                                                  | The standard holds regardless of who or what writes the code.                                                                                                                                                                                                               |
| Settings are checked once at startup; wrong values stop the server, missing values only mark the features that need them as not ready | A bad value fails loudly at the start instead of deep inside a PayPal call, while the server can still run before every key is added. `pnpm env:check` shows the status without printing values.                                                                            |
| Secret settings are wrapped so printing, logging or serializing them shows `[redacted]`                                               | Secrets must never reach logs, even by accident.                                                                                                                                                                                                                            |
| The PayPal API address is fixed to the sandbox, not a setting                                                                         | Live money is out of scope ([scope.md](scope.md)); a wrong setting must never reach real PayPal.                                                                                                                                                                            |
| The server is bundled with esbuild, and the build is part of `pnpm verify`                                                            | Packages stay TypeScript source with no build of their own; bundling compiles them into the server's runnable output, while npm dependencies stay external so the lockfile and audit still cover them. Building in verify catches a broken build before it reaches hosting. |
